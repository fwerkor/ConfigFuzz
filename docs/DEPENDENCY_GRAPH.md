# Dependency Constraint Hypergraph

ConfigFuzz converts normalized constraints into an explicit dependency hypergraph. A graph edge is a complete constraint, not a pairwise approximation: one divisibility rule may connect three or more configuration parameters and an environment value at the same time.

## Data model

Nodes are classified as:

- `parameter`: numeric, string, enum, or structural configuration values;
- `feature`: Boolean switches and feature gates;
- `environment`: world size, device count, rank, memory limits, and related runtime context.

Each hyperedge records:

- the normalized expression;
- an optional guard and its predicate;
- all participating nodes;
- inferred drivers and dependents when direction is defensible;
- relation type;
- source evidence, confidence, component, framework, and version scope;
- validation status.

Supported relation labels include:

- `type`, `range`, and `enum`;
- `requires` and `conflicts`;
- `divisibility` and constant `alignment`;
- `bound`, `equality`, and `product_limit`;
- `environment` and `resource`;
- `conditional` and `other` for expressions that cannot be classified more narrowly.

The status vocabulary is:

- `static_candidate`;
- `dynamically_supported`;
- `confirmed`;
- `environment_specific`;
- `contradicted`.

Static environment/resource edges are marked `environment_specific` immediately. Other status transitions require runtime or manual evidence.

## Deduplication

The source scanner indexes a multi-parameter constraint under every requested participating parameter. The graph deduplicates those copies using the normalized expression and constraint kind.

For example, the following relation may appear in both the `num_attention_heads` and `tensor_model_parallel_size` result lists:

```text
num_attention_heads % tensor_model_parallel_size == 0
```

The graph stores one hyperedge:

```json
{
  "relation": "divisibility",
  "participants": [
    "num_attention_heads",
    "tensor_model_parallel_size"
  ],
  "drivers": ["tensor_model_parallel_size"],
  "dependents": ["num_attention_heads"]
}
```

Evidence from duplicate indexed copies is merged.

## Direction inference

Direction is inferred only for bounded patterns:

- in `lhs % rhs == 0`, parameters in `rhs` drive parameters in `lhs`;
- in `lhs <= rhs`, parameters in `rhs` drive parameters in `lhs`;
- in `guard => predicate`, guard-only parameters drive predicate-only parameters;
- unary type/range/enum edges constrain their single parameter;
- ambiguous equalities and complex formulas remain symmetric hyperedges.

Direction represents mutation impact, not causal proof. `related_parameters(x)` uses undirected co-membership, while `affected_parameters(x)` follows only defensible directed influence and treats undirected edges symmetrically.

## Configuration paths

The graph reparses expressions independently from the scanner's parameter index. It preserves qualified paths such as:

```text
args.world_size
language_model.hidden_size
model_parallel.tensor_model_parallel_size
```

This prevents generic container roots such as `args` or `language_model` from becoming dependency nodes.

## Building a graph

`configfuzz scan` now includes a `dependency_graph` field directly:

```bash
python -m configfuzz scan \
  --parameter hidden_size \
  --parameter tensor_model_parallel_size \
  --output scan.json \
  /path/to/framework
```

A graph can also be rebuilt from an existing scan artifact:

```bash
python -m configfuzz graph scan.json \
  --framework Megatron-LM \
  --version 42460a7 \
  --output graph.json
```

Versioned framework scans generated by `scripts/run_framework_static_scan.py` embed the graph and global framework scope automatically.

## Queries

The Python API provides:

```python
from configfuzz.dependencies import DependencyGraph

graph = DependencyGraph.from_scan_payload(payload)

graph.constraints_for("tensor_model_parallel_size")
graph.related_parameters("tensor_model_parallel_size")
graph.affected_parameters("tensor_model_parallel_size")
graph.connected_components()
graph.active_constraints(current_config)
```

A constraint guard is evaluated against a flat or nested configuration mapping. Unsupported expressions and missing values remain unknown rather than being treated as false.

## Joint mutation planning

The first planner keeps the requested parameter value fixed, follows affected edges, and attempts bounded repairs for:

- direct divisibility;
- constant alignment;
- direct equality;
- simple numeric upper/lower bounds;
- Boolean requirements and conflicts.

Example baseline:

```json
{
  "hidden_size": 4096,
  "tensor_model_parallel_size": 4
}
```

Request:

```bash
python -m configfuzz plan-mutation graph.json baseline.json \
  --parameter tensor_model_parallel_size \
  --value 6 \
  --output plan.json
```

For the included fixture, the planner proposes:

```json
{
  "tensor_model_parallel_size": 6,
  "hidden_size": 4104
}
```

`4104` is both divisible by the requested TP value and aligned to the declared multiple of eight.

A plan also reports:

- affected parameters;
- validation order;
- impacted edge IDs;
- remaining violated edges;
- unresolved edges;
- missing context values.

The planner does not silently mutate environment nodes such as `world_size`. An incompatible environment relation remains violated or unresolved so that the execution harness can reject, reschedule, or probe it explicitly.

## Z3 joint solving

`solve-mutation` compiles the supported portion of the impacted graph component
into Z3. The requested parameter value is fixed, environment nodes remain fixed,
and only parameters reachable through inferred dependency direction may change.
The optimizer first minimizes violated static-candidate weight, then minimizes
the number of changed parameters and their numeric distance from the baseline.

```bash
python -m configfuzz solve-mutation graph.json baseline.json \
  --parameter tensor_model_parallel_size \
  --value 6 \
  --output solver-plan.json
```

Constraint status determines enforcement:

- `confirmed`, `dynamically_supported`, and `environment_specific` edges are hard;
- `static_candidate` edges are weighted soft constraints by default;
- `contradicted` edges are excluded;
- `--static-hard` converts static candidates to hard constraints for controlled
  experiments.

The solver currently compiles integer/real/Boolean/string types, arithmetic,
comparisons, divisibility, literal enums, conjunction/disjunction, implications,
conditional expressions, and bounded `min`/`max`/`abs` calls. Unsupported edges
are reported in `unsupported_edges`; unrelated graph edges are reported in
`out_of_scope_edges`. Neither class is silently approximated.

The included fixture changes TP from 4 to 6 and obtains:

```json
{
  "tensor_model_parallel_size": 6,
  "hidden_size": 4104
}
```

All six impacted static formulas are satisfied, including TP divisibility and
the declared multiple-of-eight alignment.

## Runtime feedback

`apply-feedback` evaluates labeled probe samples against the edges involving the
mutated parameter and updates status, confidence, dynamic evidence, and cumulative
per-edge counters:

```bash
python -m configfuzz apply-feedback \
  graph.json samples.json baseline.json \
  --output feedback-graph.json
```

The attribution rules are deliberately asymmetric:

- a `VALID` sample that violates an active edge contradicts that edge;
- a `VALID` sample satisfying an edge provides positive support;
- an `INVALID` sample supports an edge only when exactly one evaluable active
  edge is violated;
- multiple violated edges make the invalid sample ambiguous;
- `UNKNOWN` is ignored;
- `POTENTIAL_BUG` is recorded only as bug-preserving evidence and never becomes
  invalid-domain evidence.

An edge becomes `confirmed` after at least three valid supports and one isolated
invalid support. Any valid counterexample immediately marks it `contradicted`.
Exact feedback batches are fingerprinted, so importing the same baseline and
sample set twice does not inflate confidence.

On the real lm-sv hidden-size probe, runtime feedback confirms:

```text
hidden_size % tensor_model_parallel_size == 0
```

using five valid samples and two isolated invalid samples. It contradicts the
unconditional candidate:

```text
ffn_hidden_size <= hidden_size * 6
```

because three values accepted by the validator violate that formula. This is
evidence that the latter is a repair policy or a conditionally scoped relation,
not a global hard validity requirement.

## Limitations

The first planner is deliberately bounded. It does not yet:

- solve arbitrary nonlinear, quantified, or higher-order constraints;
- reason about resource models;
- infer causal direction for ambiguous formulas;
- generate deliberate single-edge violations;
- write mutations back into lm-sv's execution path.

The next integration stage should add adaptive counterexample selection, valid
boundary generation, deliberate one-edge violations, and direct lm-sv mutation
execution from solver plans.
